## 6 后端公共构件实现

后台管理系统的全部业务接口都建立在四个公共构件上：数据库连接、令牌鉴权、口令加密与响应封装。它们分别解决“连得上库”“认得出人”“存得住口令”“说得清结果”四个问题，一旦规则不统一，后续每新增一个模块都要重复处理同类问题，异常也就无法收敛。因此本章把这四处实现单独成节，既作为编码依据，也作为实训过程中自查的基准。

**实现位置与依赖关系：**配置由 config 包统一读取环境变量，db 包依赖配置拼装 DSN 并建立 GORM 连接；utils 包提供 JWT 与 bcrypt 两个与业务无关的工具；response 包向上被 controller 与 middleware 共同调用，向下依赖 utils 中的业务异常类型。四者之间没有循环依赖，新增业务模块时可直接复用。

### 6.1 数据库连接初始化

**实现思路：**启动时读取环境变量中的主机、端口、账号、库名与连接池参数，拼装带 parseTime 与 loc 的 DSN，交给 GORM 打开连接；随后从 GORM 取出底层 *sql.DB 设置最大连接数、空闲连接数与连接存活时间，再用带超时的 Ping 做一次连通性校验。任一步失败立即返回错误，由入口函数终止启动，避免服务带病运行、请求到达后才发现数据库不可用。

**日志打印：**GORM 的日志器按运行模式分级——调试模式打印全部 SQL 与执行耗时，便于对照接口核对语句；发布模式只保留慢查询与错误。慢查询阈值取 200 毫秒，超过即记录，这为后续性能优化留下可查线索；查询不到记录属于正常业务分支（如账号不存在），因此开启忽略该错误，防止日志被无效告警填满。

```go
package db

import (
	"context"
	"log"
	"os"
	"time"

	"gorm.io/driver/mysql"
	"gorm.io/gorm"
	gormlogger "gorm.io/gorm/logger"

	"industrial_admin/config"
	"industrial_admin/model"
)

// DB 是全局数据库句柄。
// 约定：只在 db 包内赋值，其他包一律通过 db.DB 使用，避免出现多处各自 Open 连接。
var DB *gorm.DB

// newLogger 构造 GORM 日志器，控制 SQL 打印级别与慢查询阈值。
// debug 模式打印全部 SQL，方便联调；release 模式只打印慢查询与错误，避免日志刷屏。
func newLogger(cfg *config.Config) gormlogger.Interface {
	level := gormlogger.Warn
	if cfg.App.Mode == "debug" {
		level = gormlogger.Info
	}
	return gormlogger.New(
		// 输出目标为标准输出，运行日志由部署环境统一收集
		log.New(os.Stdout, "[GORM] ", log.LstdFlags),
		gormlogger.Config{
			SlowThreshold: 200 * time.Millisecond, // 超过 200ms 记为慢查询
			LogLevel:      level,
			// 查询不到记录属于正常业务分支（如账号不存在），不打错误日志
			IgnoreRecordNotFoundError: true,
			Colorful:                  false, // 日志落文件时不带颜色控制符
		},
	)
}

// Init 读取配置建立 MySQL 连接，设置连接池并做一次连通性校验。
// 调用方（main.go）在返回错误时必须终止启动，避免带病运行。
func Init(cfg *config.Config) error {
	conn, err := gorm.Open(mysql.Open(cfg.DB.DSN()), &gorm.Config{
		Logger: newLogger(cfg),
		// 单条写入默认不包事务，需要原子性时在 service 层显式使用 Transaction
		SkipDefaultTransaction: true,
		// 统一使用本机时区生成时间戳，避免与 MySQL 时区不一致导致偏差
		NowFunc: func() time.Time { return time.Now().Local() },
	})
	if err != nil {
		return err
	}

	// 取出底层 *sql.DB，用于设置连接池参数
	sqlDB, err := conn.DB()
	if err != nil {
		return err
	}

	sqlDB.SetMaxOpenConns(cfg.DB.MaxOpen)           // 最大打开连接数，防止高并发压垮数据库
	sqlDB.SetMaxIdleConns(cfg.DB.MaxIdle)           // 最大空闲连接数，过小会导致频繁建连
	sqlDB.SetConnMaxLifetime(time.Hour)             // 连接最长存活 1 小时，规避 MySQL 主动断连
	sqlDB.SetConnMaxIdleTime(10 * time.Minute)      // 空闲超过 10 分钟即释放

	// Ping 必须带超时：数据库不可达时不能把启动流程挂死
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	if err := sqlDB.PingContext(ctx); err != nil {
		return err
	}

	DB = conn
	log.Printf("数据库连接成功：%s@%s:%d/%s", cfg.DB.User, cfg.DB.Host, cfg.DB.Port, cfg.DB.DBName)
	return nil
}

// AutoMigrate 把 model 结构体同步为表结构，仅开发阶段使用。
// 正式交付以 industrial_admin.sql 建表：自动迁移不会补外键、索引注释，也无法回滚。
func AutoMigrate() error {
	return DB.AutoMigrate(
		&model.Dept{},
		&model.User{},
		&model.Role{},
		&model.Permission{},
		&model.UserRole{},
		&model.RolePermission{},
		&model.SysConfig{},
		&model.OperationLog{},
	)
}

// Close 释放连接池，由 main.go 在优雅退出时调用。
func Close() error {
	sqlDB, err := DB.DB()
	if err != nil {
		return err
	}
	return sqlDB.Close()
}
```

### 6.2 JWT 令牌签发与解析

**实现目的：**前后端分离后，服务端不再依赖会话保持登录状态，改为签发令牌、由客户端每次请求携带。本系统采用 HS256 对称签名：服务端与签发方共用同一密钥，令牌被改动任意一个字符，签名校验即失败，因此不需要在数据库保存会话记录，也便于水平扩容。

**载荷设计：**令牌只放用户标识与账号，不放手机号、角色明细等可被 Base64 解码查看的信息；有效期默认 2 小时，由 JWT_EXPIRE_HOURS 控制。过期时间交给标准库维护，解析时自动校验，避免手工比较时间导致边界判断出错。

```go
package utils

import (
	"errors"
	"fmt"
	"time"

	jwt "github.com/golang-jwt/jwt/v5"

	"industrial_admin/config"
)

// 令牌解析的几类失败原因，便于上层区分提示文案
var (
	ErrTokenEmpty   = errors.New("令牌为空")
	ErrTokenInvalid = errors.New("令牌无效")
	ErrTokenExpired = errors.New("令牌已过期")
)

// Claims 是自定义载荷。
// 只放身份标识（用户 ID、账号），不放手机号、角色明细等可被解码读取的信息；
// RegisteredClaims 提供标准字段（签发方、签发时间、过期时间）。
type Claims struct {
	UserID   uint64 `json:"uid"`
	Username string `json:"uname"`
	jwt.RegisteredClaims
}

// GenerateToken 为登录成功的用户签发令牌。
// 返回：令牌串、过期时间（毫秒，供前端倒计时或自动刷新使用）。
// 私钥来自环境变量 JWT_SECRET，泄露即等于所有账号可被伪造，因此禁止写入代码库。
func GenerateToken(cfg *config.Config, userID uint64, username string) (string, int64, error) {
	now := time.Now()
	exp := now.Add(cfg.JWT.Expire) // 有效期由 JWT_EXPIRE_HOURS 控制，默认 2 小时

	claims := Claims{
		UserID:   userID,
		Username: username,
		RegisteredClaims: jwt.RegisteredClaims{
			Issuer:    cfg.JWT.Issuer,          // 签发方，解析时可校验来源
			IssuedAt:  jwt.NewNumericDate(now), // 签发时间
			ExpiresAt: jwt.NewNumericDate(exp), // 过期时间，由库自动校验
		},
	}

	// 使用 HS256（对称加密），密钥必须在服务端保管
	token := jwt.NewWithClaims(jwt.SigningMethodHS256, claims)
	signed, err := token.SignedString([]byte(cfg.JWT.Secret))
	if err != nil {
		return "", 0, err
	}
	return signed, exp.UnixMilli(), nil
}

// ParseToken 校验令牌并取出载荷。
// 校验项：签名是否被篡改、是否已过期、签名算法是否为预期的 HMAC。
// 只要返回错误，调用方一律按未登录处理（HTTP 401），不要把具体原因回传给前端。
func ParseToken(cfg *config.Config, tokenStr string) (*Claims, error) {
	if tokenStr == "" {
		return nil, ErrTokenEmpty
	}

	claims := &Claims{}
	_, err := jwt.ParseWithClaims(tokenStr, claims, func(t *jwt.Token) (any, error) {
		// 关键防护：只接受 HMAC 系列算法，防止攻击者把 alg 改成 none 绕过签名
		if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
			return nil, fmt.Errorf("非预期的签名算法: %v", t.Header["alg"])
		}
		return []byte(cfg.JWT.Secret), nil
	})
	if err != nil {
		// 过期属于可预期分支，单独归类，方便前端提示“登录已失效，请重新登录”
		if errors.Is(err, jwt.ErrTokenExpired) {
			return nil, ErrTokenExpired
		}
		return nil, ErrTokenInvalid
	}
	return claims, nil
}
```

图2 JWT 签发与解析代码（utils/jwt.go）

**安全处理：**解析阶段显式校验签名算法必须为 HMAC 系列。若不校验，攻击者可将算法头改为 none，构造无签名令牌绕过验证，这是 JWT 使用中最常见的漏洞。解析失败时区分“过期”与“无效”两类原因：前者提示用户重新登录，后者不暴露具体细节，避免为探测者提供额外信息。

**与鉴权中间件的衔接：**鉴权中间件从 Authorization 头取出 Bearer 令牌交给 ParseToken，校验通过后把用户标识写入请求上下文，供控制器与权限中间件读取；同时再查一次账号状态，使停用或删除的账号即使令牌未过期也立刻失效。

### 6.3 bcrypt 口令加盐哈希

**存储原则：**数据库只保存 password_hash 一列，不存明文、不另设盐列。bcrypt 输出形如 $2b$10$……，算法版本、代价因子与随机盐已内嵌在字符串中，同一明文每次加密结果都不同，因此“加盐”不需要额外字段承载，也不会因为盐管理不当导致全库同口令同哈希。

```go
package utils

import (
	"fmt"

	"golang.org/x/crypto/bcrypt"
)

const (
	// BcryptCost 计算代价：2^10 次迭代，单次哈希约 10~50ms。
	// 值越大越难暴力破解，但会同步拖慢登录接口，课程项目取 10 即可。
	BcryptCost = 10

	// MinPasswordLength 口令最短长度，注册与重置口令共用同一规则。
	MinPasswordLength = 8

	// MaxPasswordBytes bcrypt 输入上限为 72 字节，超出部分会被静默截断，
	// 因此必须在入库前拦截，避免“超长口令只校验了前 72 字节”。
	MaxPasswordBytes = 72
)

// ValidatePassword 校验口令是否符合策略。
// 返回的错误文案可直接展示给用户，由控制器转成 40001 参数错误。
func ValidatePassword(plain string) error {
	if len(plain) < MinPasswordLength {
		return fmt.Errorf("口令长度不得少于 %d 位", MinPasswordLength)
	}
	if len([]byte(plain)) > MaxPasswordBytes {
		return fmt.Errorf("口令过长，不能超过 %d 字节", MaxPasswordBytes)
	}
	return nil
}

// HashPassword 把明文口令转换为 bcrypt 哈希。
// 返回的字符串形如 $2b$10$xxxxx，其中已内嵌算法版本、代价因子与随机盐，
// 因此数据库只需要一个 password_hash 字段，不必单独保存盐；
// 同一明文每次调用得到的哈希都不同，这是加盐的直接体现。
func HashPassword(plain string) (string, error) {
	if err := ValidatePassword(plain); err != nil {
		return "", err
	}

	hashed, err := bcrypt.GenerateFromPassword([]byte(plain), BcryptCost)
	if err != nil {
		return "", err
	}
	return string(hashed), nil
}

// VerifyPassword 登录时比对明文口令与库中哈希。
// bcrypt 会从哈希串中取出盐重算摘要并做常量时间比较，因此：
//   - 不需要（也无法）手工加盐；
//   - 比较过程不因前缀匹配而提前返回，可抵御时序攻击；
//   - 返回 true 表示口令正确，false 表示口令错误（不区分“哈希损坏”与“口令错误”，
//     避免给攻击者提供额外信息）。
func VerifyPassword(hash, plain string) bool {
	if hash == "" || plain == "" {
		return false
	}
	return bcrypt.CompareHashAndPassword([]byte(hash), []byte(plain)) == nil
}
```

图3 口令加盐哈希与比对代码（utils/password.go）

**比对机制：**登录时用 CompareHashAndPassword 从哈希串中取出盐重算摘要并做常量时间比较。常量时间意味着无论前几位是否相同，耗时都不随匹配长度变化，可抵御通过响应时间逐位猜测口令的时序攻击。代价因子取 10，单次哈希约十至数十毫秒，足以抬高批量暴力破解成本，同时不会明显拖慢登录。

**边界处理：**bcrypt 输入上限为 72 字节，超出部分会被静默截断，若不拦截就会出现“超长口令只校验了前 72 字节”的隐患；口令最短 8 位由统一的校验函数在接口入口处拦截，返回参数错误而非等到哈希环节报服务器错误。

**表2 口令工具函数职责**

| 函数 | 调用场景 | 行为说明 |
| :--- | :--- | :--- |
| ValidatePassword | 注册、重置口令 | 校验长度与字节上限，错误文案可直接展示 |
| HashPassword | 注册、重置口令 | 校验后生成 bcrypt 哈希，返回 $2b$10$ 开头的 60 位字符串 |
| VerifyPassword | 登录 | 比对明文与哈希，返回布尔值，不区分“口令错”与“哈希损坏” |

### 6.4 统一响应封装

**封装目标：**前后端约定固定结构 {code, message, data}，前端只需一套拦截器即可处理全部接口：按 code 判断成功与否，按 message 展示提示，按 data 取业务数据。若不统一，每个接口返回形态各异，前端要逐接口写解析逻辑，异常提示也无法集中管理。

**业务码与状态码的关系：**业务码表达“发生了什么”，HTTP 状态码表达“请求是否被受理”。两者由同一份映射表联动：参数错误对应 400，未登录对应 401，越权对应 403，资源不存在对应 404，唯一约束冲突对应 409，未预期错误对应 500。这样前端既可按状态码统一拦截，也可按业务码做细分提示。

```go
package response

import "net/http"

// 业务错误码：与前端拦截器约定一致，0 表示成功
const (
	CodeSuccess      = 0
	CodeParamInvalid = 40001
	CodeUnauthorized = 40100
	CodeForbidden    = 40300
	CodeNotFound     = 40400
	CodeConflict     = 40900
	CodeServerError  = 50000
)

// HTTPStatus 业务码到 HTTP 状态码的映射
func HTTPStatus(code int) int {
	switch code {
	case CodeSuccess:
		return http.StatusOK
	case CodeParamInvalid:
		return http.StatusBadRequest
	case CodeUnauthorized:
		return http.StatusUnauthorized
	case CodeForbidden:
		return http.StatusForbidden
	case CodeNotFound:
		return http.StatusNotFound
	case CodeConflict:
		return http.StatusConflict
	default:
		return http.StatusInternalServerError
	}
}
```

图4 业务错误码定义（response/code.go）

```go
package response

import (
	"errors"
	"net/http"
	"time"

	"github.com/gin-gonic/gin"

	"industrial_admin/utils"
)

// Body 是全项目唯一的响应外壳，结构固定为 {code, message, data}。
// 额外附带 timestamp，便于前端排查“旧响应被缓存”的问题。
// 约定：任何接口都不得自行拼装 JSON，一律通过本文件的函数输出。
type Body struct {
	Code      int    `json:"code"`      // 业务码，0 表示成功
	Message   string `json:"message"`   // 提示文案，可直接展示
	Data      any    `json:"data"`      // 业务数据，失败时为 null
	Timestamp int64  `json:"timestamp"` // 服务器时间戳（毫秒）
}

// PageData 是列表接口的标准数据体。
// 前端表格组件只需读取 list 渲染行、total 计算分页总数。
type PageData struct {
	List     any   `json:"list"`     // 当前页数据
	Total    int64 `json:"total"`    // 记录总数
	Page     int   `json:"page"`     // 当前页码，从 1 开始
	PageSize int   `json:"pageSize"` // 每页条数
}

// OK 输出成功响应，业务码固定为 0。
func OK(c *gin.Context, data any) {
	c.JSON(http.StatusOK, Body{
		Code:      CodeSuccess,
		Message:   "ok",
		Data:      data,
		Timestamp: time.Now().UnixMilli(),
	})
}

// Success 与 OK 等价，保留两个命名便于在代码中表达“查询成功/操作成功”的语义。
func Success(c *gin.Context, data any) { OK(c, data) }

// Page 输出分页成功响应，把 list、total、page、pageSize 收进 data。
func Page(c *gin.Context, list any, total int64, page, pageSize int) {
	OK(c, PageData{List: list, Total: total, Page: page, PageSize: pageSize})
}

// Abort 输出失败响应并终止后续处理，专供中间件使用。
// 与 Fail 的差别：AbortWithStatusJSON 会阻止后续 handler 继续执行，
// 否则鉴权失败后仍会进入业务逻辑，形成越权风险。
func Abort(c *gin.Context, code int, message string) {
	c.AbortWithStatusJSON(HTTPStatus(code), Body{
		Code:      code,
		Message:   message,
		Data:      nil,
		Timestamp: time.Now().UnixMilli(),
	})
}

// Fail 输出失败响应，供控制器使用。
// HTTP 状态码由业务码映射得到，保证前端既能按状态码拦截，也能按业务码细分提示。
func Fail(c *gin.Context, code int, message string) {
	c.JSON(HTTPStatus(code), Body{
		Code:      code,
		Message:   message,
		Data:      nil,
		Timestamp: time.Now().UnixMilli(),
	})
}

// Error 是控制器的统一错误出口。
// service 层返回 *utils.AppError 时按其错误码输出；其余（数据库报错、空指针等）
// 统一收敛成 50000，绝不把底层错误细节暴露给调用方。
func Error(c *gin.Context, err error) {
	var ae *utils.AppError
	if errors.As(err, &ae) {
		Fail(c, ae.Code, ae.Message)
		return
	}
	Fail(c, CodeServerError, "服务器内部错误")
}
```

图5 统一响应结构与输出函数（response/response.go）

**两类失败出口：**Fail 供控制器使用，Abort 供中间件使用。二者的差别在于 Abort 会终止后续处理链，鉴权与权限校验失败必须用它，否则请求仍会继续进入业务逻辑，形成越权风险。Error 是控制器的统一出口：业务层返回 AppError 时按其错误码输出，其余数据库错误、运行时异常统一收敛为服务器内部错误，绝不把底层错误细节暴露给调用方。

**表3 统一错误码与返回场景**

| 业务码 | HTTP 状态 | 典型场景 |
| :--: | :--: | :--- |
| 0 | 200 | 登录成功、查询成功、操作成功 |
| 40001 | 400 | 参数缺失、参数格式错误、口令长度不足 |
| 40100 | 401 | 未携带令牌、令牌过期或被篡改、口令错误、账号已停用 |
| 40300 | 403 | 已登录但缺少接口所需权限点，同时写入一条失败操作日志 |
| 40400 | 404 | 记录不存在、接口路径不存在 |
| 40900 | 409 | 账号、角色编码、部门编码重复 |
| 50000 | 500 | 数据库异常、未预期的运行时 panic |

### 6.6 本章小结

四个公共构件的价值不在代码量，而在规则统一：连接层负责“稳定连上”，令牌层负责“安全认出”，口令层负责“不可逆存储”，响应层负责“统一表达”。实训过程中，凡是新增接口出现提示文案不一致、错误码混乱或越权未被拦截，问题几乎都能回溯到这四处的某一条约定没有被遵守。因此后续开发应把本章作为编码基线：新模块只写业务规则，公共处理一律复用现有实现，不另行拼装。
