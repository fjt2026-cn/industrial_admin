# 基于工业软件企业后台管理系统数字化运营

综合实训总结报告

## 摘要

本报告是工业软件开发综合实训（课程代码 192434303，156 学时）的总结报告，实训题目为"基于工业软件企业后台管理系统数字化运营"。实训期间我独立完成了一套前后端分离的企业后台管理系统：后端使用 Go 1.25 + Gin + GORM，前端使用 Vue 3 + Element Plus + Axios + ECharts，数据库使用 MySQL 8.0，按"需求确认—概要设计—数据库设计—后端编码—前端联调—接口测试—部署运行"的顺序推进，全部代码与文档托管在 GitHub 仓库。

系统实现了登录与图形化运营看板、用户管理、角色与权限（RBAC）、部门树管理、系统参数配置、操作日志查询六大模块，对外提供 25 个 RESTful 接口，统一返回 {code, message, data} 结构，接口按权限点做细粒度控制；涉及用户创建、角色授权、部门删除等一致性操作一律使用数据库事务；口令以 bcrypt 加盐哈希入库，令牌使用 HS256 签名的 JWT。

成果方面，共形成数据库脚本 1 份（8 张表、幂等可重复执行）、后端源码 40 余个文件与前端 4 个业务页面，撰写分章说明文档 12 份；接口测试执行 48 条用例、覆盖 6 个模块，最终全部通过，测试过程中发现并修复 2 处缺陷；后端编译为 20.1 MB 单文件可执行程序，前端打包产出 2.44 MB 静态资源，在本机完成部署并经浏览器访问验证登录、看板、用户管理与角色授权均可用。

## 3 需求分析

### 3.1 业务背景与使用角色

工业软件企业的数字化运营，落到后台管理系统上就是三件事：把人和组织管清楚、把权限管住、把运营数据看得见。据此我把系统使用者分为三类：系统管理员负责账号、角色与权限点的维护；部门主管负责本部门人员与组织结构的调整；普通员工只能查看与自己权限相关的数据。三类角色的差别不靠页面隐藏实现，而是靠接口层的权限点校验保证，这也是后面做 RBAC 与越权测试的出发点。

### 3.2 功能需求

按任务书要求的功能范围，我把系统拆成六大模块，并把每个模块的功能点与对应的数据表对应起来，功能清单见表 3。模块之间共用同一套用户、角色、权限与部门数据，看板与日志则是对这些数据的二次加工。

**表 3 功能需求清单**

| 模块 | 主要功能点 | 涉及数据表 |
| :--- | :--- | :--- |
| 登录与鉴权 | 账号口令登录、令牌签发、当前用户信息、退出 | user、operation_log |
| 用户管理 | 分页与关键字查询、新增、编辑、删除、重置口令、用户角色绑定 | user、user_role、dept |
| 角色与权限（RBAC） | 角色增删改查、权限点维护、按角色授权、已授权查询 | role、permission、role_permission |
| 部门管理 | 部门树查询、平铺列表、新增、编辑（含层级校验）、删除 | dept |
| 系统参数配置 | 参数列表、单条读取、单条修改、批量修改（全成才生效） | sys_config |
| 操作日志 | 关键操作自动留痕、按模块/结果/关键字条件查询、分页 | operation_log |
| 运营数据看板 | 概览指标、用户增长、用户活跃度、日志频次统计 | user、operation_log |

### 3.3 非功能需求

除功能之外，任务书还提出了几项工程性要求，我把它转成可检查的指标：一是安全，口令必须哈希存储、所有查询走参数化、接口必须鉴权并按权限点控制、敏感信息不出现在代码与前端；二是数据一致性，用户创建、角色授权这类"要么全成要么全不成"的操作必须放在事务里；三是可维护，接口返回格式统一、错误码集中定义、代码按职责分层；四是可用性，页面要有加载态、错误提示与空数据提示，中文不乱码；五是多端可部署，后端能编译成单文件运行，前端能打包成静态资源并由代理访问后端。

### 3.4 业务规则与边界

需求阶段我明确了几条业务规则，后面的编码与测试都以此为依据：账号全局唯一且长度不超过 50 字符，口令不超过 72 字节（bcrypt 的有效长度上限）；口令连续错误 5 次锁定 10 分钟；内置角色与内置管理员账号不允许删除；部门编码全局唯一、同级名称唯一，上级不能是自己、不能是自己的下级；角色授权采用整体替换而不是增量追加。同时明确不做的事情：不做文件导入导出与消息通知，不做多租户隔离，数据权限只做到功能权限（权限点）层面，这些在报告第 9 章列为后续改进方向，避免报告里出现无据的"已实现"。

## 4 系统设计

### 4.1 总体架构

系统采用 B/S 架构与前后端分离：浏览器加载 Vue 3 打包后的静态页面，页面里的所有数据请求都以 /api/v1 相对路径发出；发布前端时由一层代理（开发期为 Vite 代理，部署期为 Vite preview 或 Nginx）把 /api 请求转发到 Go 服务；Go 服务内部按 MVC 思路分层，控制器只做参数解析与响应封装，业务规则与事务边界放在服务层，数据访问统一交给 GORM，最后由 MySQL 落库。分层与职责见表 4。

**表 4 系统分层与职责**

| 层次 | 职责 | 主要载体 |
| :--: | :--- | :--- |
| 表现层 | Vue 3 页面与组件、Element Plus 交互、ECharts 图表 | web/src/views、layout、api |
| 接入层 | 代理转发 /api、CORS、令牌携带 | vite.config.js、middleware/cors.go |
| 控制器层 | 参数绑定与校验、调用服务、封装统一响应 | controller/*.go |
| 服务层 | 业务规则、事务边界、统计聚合 | service/*.go |
| 持久层 | 结构体与表映射、参数化查询、连接池 | model/*.go、db/db.go |
| 数据层 | 8 张表、主外键、唯一索引、软删除字段 | sql/industrial_admin.sql |

### 4.2 技术选型

选型原则是"够用、能讲清、可复现"，每一项技术都对应任务书里的一个要求，而不是为了堆技术。具体选型与理由见表 5。

**表 5 技术选型与理由**

| 技术 | 角色 | 选择理由 |
| :--- | :--: | :--- |
| Gin | HTTP 框架 | 轻量、中间件机制清晰，适合演示鉴权与权限拦截 |
| GORM | ORM | 结构体映射表、链式条件查询、事务封装，参数化查询天然防注入 |
| MySQL 8.0 | 关系库 | 支持窗口函数与外键约束，utf8mb4 可直接存中文与表情符号 |
| JWT（HS256） | 无状态令牌 | 服务端无需存会话，前端放 Authorization 头即可 |
| bcrypt | 口令哈希 | 自带 salt、可调代价，满足"禁止明文存储" |
| Vue 3 + Element Plus | 前端框架与组件库 | 组合式 API 上手快，表格、弹窗、树控件齐全 |
| Axios | HTTP 客户端 | 拦截器统一注入令牌与处理错误码 |
| ECharts | 图表库 | 柱线双轴、多折线、图例与自适应，满足看板需求 |

### 4.3 数据库概念设计

概念设计阶段我画了 E-R 图，核心实体七个：用户、角色、权限点、部门、系统配置、操作日志，以及两张关联实体（用户—角色、角色—权限）。实体关系可以这样描述：一个部门下可以有多个用户，一个部门又可以挂在另一个部门下形成组织树；一个用户可以拥有多个角色，一个角色可以授权多个权限点，于是用户通过"用户—角色—权限点"三级关联拿到最终权限集合；权限点自身也有父子关系，用来表达菜单与按钮的从属；系统配置与操作日志独立于权限体系，其中操作日志只记录操作人快照而不建外键，这样即使用户被删除，历史日志仍可追溯。

按第三范式要求，我把所有多对多关系拆成独立的关联表，避免在用户表里用字符串存多个角色；同时给常用查询路径补了索引：用户表的 username 唯一索引、dept_id 与 status 普通索引，日志表的 created_at、user_id 与 (module, created_at) 组合索引，使日志按模块加时间的条件查询不必全表扫描。

### 4.4 关系模式

把 E-R 图转换成关系模式后共 8 张表，主键统一为自增 BIGINT，时间字段统一 created_at / updated_at，可软删除的表带 deleted_at。关系模式如下（下划线表示主键，花括号表示外键）：

**表 6 关系模式**

| 表名 | 主要属性 |
| :--- | :--- |
| dept | id, parent_id, dept_name, dept_code, leader_id, sort_no, status, remark, created_at, updated_at, deleted_at |
| user | id, username, password_hash, real_name, email, phone, dept_id, status, lock_until, last_login_at, last_login_ip, remark, … |
| role | id, role_name, role_code, data_scope, is_builtin, sort_no, status, remark, created_at, updated_at, deleted_at |
| permission | id, parent_id, perm_name, perm_code, perm_type, route_path, api_path, icon, sort_no, status, … |
| user_role | id, user_id, role_id |
| role_permission | id, role_id, perm_id |
| sys_config | id, config_key, config_name, value_type, category, is_system, status, remark, … |
| operation_log | id, user_id, username, module, action, method, url, ip, param, result, error_msg, cost_ms, created_at |

### 4.5 主要表结构

用户表是权限体系的入口，除基本信息外还保存口令哈希、锁定时间与最近登录信息。口令字段长度按 bcrypt 的 60 字符留出余量，字段注释直接写明"禁止存明文"。用户与部门之间通过 dept_id 外键关联，删除部门受限制，避免出现悬空人员。

**表 7 用户表 user**

| 字段 | 类型 | 说明 |
| :--- | :--: | :--- |
| id | BIGINT UNSIGNED | 主键，自增 |
| username | VARCHAR(50) | 登录账号，唯一索引 uk_user_username |
| password_hash | VARCHAR(100) | bcrypt 加盐哈希，禁止存明文 |
| real_name | VARCHAR(50) | 姓名，必填 |
| email / phone | VARCHAR(100) / VARCHAR(20) | 联系方式，可为空 |
| dept_id | BIGINT UNSIGNED | 所属部门，外键指向 dept.id |
| status | TINYINT | 1 启用，0 停用 |
| lock_until | DATETIME | 锁定截止时间，NULL 表示未锁定 |
| last_login_at / last_login_ip | DATETIME / VARCHAR(45) | 最近登录时间与 IP，兼容 IPv6 |
| deleted_at | DATETIME | 软删除时间，NULL 表示未删除 |

角色表保存角色名称、编码与内置标记。内置角色（如 super_admin）不允许改权限、不允许删除，这是为了保证系统总有一个可用的管理入口；data_scope 字段预留给数据权限，本期只做展示不做过滤，这一点在需求边界中已声明。

**表 8 角色表 role**

| 字段 | 类型 | 说明 |
| :--- | :--: | :--- |
| id | BIGINT UNSIGNED | 主键 |
| role_name | VARCHAR(50) | 角色名称，唯一索引 |
| role_code | VARCHAR(50) | 角色编码，唯一索引 |
| data_scope | TINYINT | 数据范围（预留字段） |
| is_builtin | TINYINT | 1 内置角色，禁止改权限与删除 |
| sort_no / status | INT / TINYINT | 排序号与启停状态 |

权限点表把"菜单、按钮、接口"三类权限统一成一张表，用 perm_type 区分，perm_code 采用"模块:动作"的命名，与后端路由上挂的权限码一一对应；自关联的 parent_id 表示菜单父子结构，前端授权树就是按这层关系渲染的。

**表 9 权限点表 permission**

| 字段 | 类型 | 说明 |
| :--- | :--: | :--- |
| id | BIGINT UNSIGNED | 主键 |
| parent_id | BIGINT UNSIGNED | 上级权限点，自关联外键 |
| perm_name | VARCHAR(64) | 权限点名称 |
| perm_code | VARCHAR(100) | 权限编码（模块:动作），唯一索引，与路由挂载一致 |
| perm_type | TINYINT | 1 菜单，2 按钮，3 接口 |
| route_path / api_path | VARCHAR | 菜单对应的前端路由 / 接口对应的后端路径 |
| sort_no / status | INT / TINYINT | 排序与启停 |

两张关联表结构简单但约束很关键：user_role 与 role_permission 都在组合字段上建唯一索引，防止同一用户重复绑定同一角色、同一角色重复授权同一权限点；外键在删除父表记录时限制或级联清理，保证不会留下孤立的授权关系。

**表 10 关联表与部门表关键约束**

| 表名 | 字段与约束 |
| :--- | :--- |
| user_role | id、user_id、role_id，唯一索引 uk_user_role(user_id, role_id) |
| role_permission | id、role_id、perm_id，唯一索引 uk_role_perm(role_id, perm_id) |
| dept | id、parent_id、dept_name、dept_code、leader_id、sort_no、status、remark，唯一索引 uk_dept_code，自关联外键 fk_dept_parent |

系统配置表用 value_type 表示值类型（1 字符串、2 整数、3 布尔、4 JSON），业务层据此做类型校验，避免把"true"当字符串存进去；config_key 采用"分类.名称"的写法并加唯一索引。操作日志表刻意只保存操作人快照与最小必要字段，param 字段只记录白名单内的关键参数并做脱敏，登录口令、令牌原文一律不落库。

**表 11 配置表与日志表要点**

| 表名 | 设计要点 |
| :--- | :--- |
| sys_config | config_key 唯一、value_type 类型区分、category 分类（base/security/business/dashboard）、is_system 内置标记 |
| operation_log | module、action、method、url、ip、param（脱敏）、result（1 成功/0 失败）、error_msg、cost_ms |

### 4.6 接口设计规范

## 5 后端实现说明

### 5.1 工程结构

后端按职责分 9 个包，入口 main.go 只负责"加载配置 → 连库 → 注册路由 → 启动服务 → 优雅退出"，业务逻辑一律下沉到 service，控制器保持轻薄，这样换框架或加接口时改动面很小。

**表 14 后端包结构**

| 目录 | 职责 |
| :--: | :--- |
| config | 环境变量读取与默认值，生成全局配置 |
| db | GORM 连接、连接池参数、可选自动迁移 |
| model | 与 8 张表一一对应的结构体 |
| controller | 参数绑定、调用服务、统一响应（9 个文件） |
| service | 业务规则、事务、统计聚合（9 个文件） |

### 5.2 配置与启动

所有配置都从环境变量读取，口令与密钥不写进代码。main.go 启动时创建 http.Server 并设置读、写、空闲超时与最大请求头，同时监听 SIGINT/SIGTERM：收到退出信号后先停止接收新请求，等待在途请求结束（最长 5 秒）再关闭数据库连接。这一点在部署时很重要——直接结束进程可能把正在执行的事务打断，而优雅退出能保证连接池与事务正常收尾。

### 5.3 统一响应与异常处理

统一响应由 response 包提供三个函数：成功时返回 {code:0, message:"ok", data}，失败时按业务码返回，控制器只需要 return 一个 error。业务层用 utils.NewAppError 构造"已知错误"（如参数非法、权限不足），用 utils.WrapAppError 包裹"未知错误"并统一成 50000，同时在日志里保留底层原因。配合 Recovery 中间件，任何 panic 都会被拦住并转成 50000，前端不会看到堆栈。

### 5.4 登录与鉴权

登录流程按"查账号—判锁定—比对口令—判状态—签发令牌—写日志"六步走。口令比对调用 bcrypt 的 CompareHashAndPassword，错误次数累计到 5 次即写入 lock_until 锁定 10 分钟；账号不存在与口令错误对外统一提示"账号或口令错误"，避免通过返回信息探测账号是否存在；成功与失败都会写一条登录日志，这是实训中期发现"登录从不写日志"缺陷后补上的。

```text
if u.LockUntil != nil && u.LockUntil.After(time.Now()) {
    s.recordLogin(u.ID, u.Username, 0, "账号已锁定", ip)
    return nil, utils.NewAppError(response.CodeUnauthorized, "账号已锁定，请稍后重试")
}
if !utils.VerifyPassword(u.PasswordHash, password) {
    fail := u.LoginFailCount + 1
    updates := map[string]any{"login_fail_count": fail}
    if fail >= maxLoginFail {
        updates["lock_until"] = time.Now().Add(lockMinutes * time.Minute)
        updates["login_fail_count"] = 0
    }
    s.db.Model(&model.User{}).Where("id = ?", u.ID).Updates(updates)
    s.recordLogin(u.ID, u.Username, 0, "账号或口令错误", ip)
    return nil, utils.NewAppError(response.CodeUnauthorized, "账号或口令错误")
}
token, exp, err := utils.GenerateToken(s.cfg, u.ID, u.Username)
```

代码 1 登录校验与令牌签发（service/auth_service.go 节选）

鉴权中间件解析 Authorization 头里的 Bearer 令牌，先校验签名与过期，再回查用户是否仍存在、状态是否为启用。之所以要多查一次库，是因为令牌签发后用户可能被停用或删除，只验签名会让已停用账号继续访问；这里把"过期"与"无效"分开提示，过期时前端可以直接引导重新登录。

### 5.5 RBAC 权限控制

权限控制放在接口层，用 RequirePerm(权限码) 挂在具体路由上。中间件用一条三表关联的查询判断"当前用户是否通过角色持有该权限点"，命中则放行，未命中记一条"越权访问"日志并返回 403。这样做的意义在测试阶段体现得很明显：用普通员工令牌调用管理员接口，能稳定得到 403/40300，说明权限不是靠前端隐藏按钮实现的。

```text
var count int64
err := db.DB.Table("permission p").
    Joins("JOIN role_permission rp ON rp.perm_id = p.id").
    Joins("JOIN user_role ur ON ur.role_id = rp.role_id").
    Where("ur.user_id = ? AND p.perm_code = ? AND p.status = 1", userID, permCode).
    Count(&count).Error
if err != nil { response.Abort(c, response.CodeServerError, "权限校验失败"); return }
if count == 0 {

    db.DB.Create(&model.OperationLog{ /* module: auth, action: forbidden */ })
    response.Abort(c, response.CodeForbidden, "权限不足")

c.Next()
```

### 5.6 部门树、参数配置与事务

部门管理的难点在层级校验。树的构造用一次查询取出全部部门再在内存中拼 children，避免递归查库；编辑时依次校验五件事：上级不能是自己、上级必须存在、不能形成环（用 isDescendant 沿 parent 链上溯，最多 32 层，既防死循环，也避免脏数据让递归层数过长）、编码唯一、同级名称唯一。删除在事务内先查子部门与成员，有下级或有成员就拒绝，通过后物理删除（这一点在测试中发现软删除会占住唯一索引后改的）。

系统配置的读取做了进程内缓存，写入时先按 value_type 校验取值（整数要能转换、布尔只接受 true/false），批量修改采用"全成才生效"的策略：任何一条校验失败就整体回滚，只有全部通过才刷新缓存，避免出现一半新值一半旧值的中间状态。角色授权同样是整体替换：事务内先清空该角色旧授权，再按去重后的集合写入，失败则回滚，测试中提交非法权限点时角色权限仍保持原值，证明事务边界设置正确。

### 5.7 操作日志

操作日志由中间件统一处理：受保护路由执行完后，按"模块 + 动作"写一条记录，记录操作人、方法、URL、IP、耗时、结果与失败原因；参数只取白名单字段并做脱敏，口令类字段直接剔除。登录这种发生在鉴权之前的行为，由 service 层显式调用 recordLogin 记录，这也是"登录日志缺失"缺陷的修复方式——中间件拿不到未登录时的用户身份，只能由业务层补。

### 5.8 统计接口

看板需要三组数据：用户增长（每天新增与累计）、用户活跃度（活跃人数、登录次数、操作次数）、操作频次（成功/失败与模块分布）。实现时把时间窗口参数统一处理：days 非法（非数字或超范围）回落默认值，上限 90 天、活跃度上限 30 天；聚合结果按日期补齐缺失的零点，保证 ECharts 的 X 轴长度稳定，不会因为某天没数据就少一个刻度。

## 6 前端实现说明

### 6.1 工程结构与依赖

前端用 Vite 手工搭建 Vue 3 工程，目录按职责划分：api 放各模块接口封装，views 放页面，layout 放整体布局，router 放路由与守卫，utils 放请求封装。依赖只有 5 个运行时包（Vue、Vue Router、Element Plus、Axios、ECharts）与 2 个开发依赖（Vite、Vue 插件），刻意不引入状态管理与 UI 主题定制，保证代码能一段一段讲清楚。

**表 15 前端目录与职责**

| 路径 | 内容 |
| :--- | :--- |
| src/api/ | auth、user、role、permission、dept、stats、dashboard 七个模块的接口函数 |
| src/utils/request.js | Axios 实例、令牌注入、错误码统一处理 |
| src/router/index.js | 路由表与登录守卫（未登录跳登录页并记住来源） |

| vite.config.js | 别名、开发代理（PROXY_TARGET 可覆盖）、打包输出 dist |

### 6.2 请求封装

request.js 做了三件事：一是 baseURL 固定为 /api/v1，所有接口只写相对路径，换环境不用改代码；二是在请求拦截器里从 localStorage 取令牌并拼成 Bearer 头；三是在响应拦截器里判 code，code 为 0 时只把 data 交给业务层，非 0 时统一弹 Element Plus 的错误提示，遇到 40100 就清掉本地令牌并跳回登录页。超时设为 10 秒，网络中断与服务端错误分开提示，避免用户看到"未知错误"。

### 6.3 路由与布局

路由采用"布局 + 子路由"的结构：登录页独立，其余业务页都挂在 layout 下，切换菜单时只替换内容区。守卫在 beforeEach 里判断令牌是否存在，未登录访问业务页会被重定向到登录页并把原地址带到 query，登录成功后直接回到原页。布局组件用 el-menu 的 router 模式驱动侧边栏，支持折叠，页头显示当前路由标题，右上角退出会清掉令牌、用户信息等四项本地存储。

### 6.4 登录页与用户管理页

登录页表单只做必要校验（账号必填、口令必填），提交后按返回的令牌与权限写入本地存储并跳转首页；口令错误、账号锁定、账号停用三种失败都按后端返回的 message 原样提示，不在前端另造文案。

用户管理页是本项目交互最复杂的页面：顶部是关键字与状态查询区，中间是表格（账号、姓名、部门、角色、状态、最近登录），底部是分页；行内提供编辑、重置口令、删除三个操作。新增与编辑共用一个弹窗，通过标题与提交接口区分；重置口令单独用小弹窗，避免误改其它字段；删除走二次确认，内置管理员 admin 的删除按钮直接禁用并给出提示。

### 6.5 角色授权页

角色授权页由"角色表格 + 授权抽屉"组成。抽屉里用 el-tree 渲染权限点，按 perm_type 分成菜单、按钮、接口三组，节点 key 用 p-<id> 前缀避免与树内部节点冲突；打开抽屉时先调 /roles/:id/permissions 取已授权集合做回显，保存时把 checked 与 halfChecked 合并后去掉前缀再提交，这样"只勾了子项"的父菜单也能正确落库。对内置角色，抽屉只读，保存按钮置灰。

### 6.6 运营数据看板

看板页上半部分是四张概览卡（用户总数、今日新增、今日操作、活跃用户），下半部分是两个 ECharts 图表：用户增长用柱线双轴（柱子是每日新增、折线是累计总数），活跃度用三条折线（活跃人数、登录次数、操作次数）。图表在 mounted 后初始化，监听窗口 resize 重算尺寸，组件卸载时 dispose 释放实例，避免路由来回切换造成内存泄漏。时间窗口提供 7 天 / 30 天 / 90 天切换，切换后重新拉取数据并整体替换 option。

### 6.7 联调与打包

联调阶段用 Vite 代理把 /api 转发到后端，代理目标支持 PROXY_TARGET 环境变量覆盖，因此后端换端口时只改环境变量。联调中发现并处理了三类问题：一是 40100 令牌过期后页面不跳转，改为拦截器统一清令牌回登录；二是 ECharts 在容器宽度变化后不重绘，补了 resize 监听；三是浏览器控制台的 favicon 404，属资源缺失，不影响功能。打包执行 npm run build，实测耗时 8.67 秒，产出 16 个文件、合计约 2.44 MB；Dashboard 分块约 1.04 MB，体积偏大来自 ECharts 整包引入，作为后续按需引入的优化点记录在案。

### 7.5 覆盖边界

### 8.2 前端打包

前端执行 npm run build，由 Vite 把组件、样式与依赖编译压缩到 dist 目录，实测耗时 8.67 秒，产出 16 个文件、合计 2 554 005 字节（约 2.44 MB）。产物是纯静态资源，任意静态服务器都能发布，但因为是单页应用并使用 history 路由，必须配置"找不到文件时回退 index.html"，否则在 /users 这类地址上刷新会 404。

```text
$env:APP_PORT = "18080"; $env:APP_MODE = "release"
$env:DB_USER = "root"; $env:DB_PASSWORD = "你的数据库口令"
$env:JWT_SECRET = "32 位以上随机串"
.\industrial_admin.exe

# 另开窗口发布前端，访问 http://127.0.0.1:4173/
cd .\web; $env:PROXY_TARGET = "http://127.0.0.1:18080"
npx vite preview --port 4173 --host 127.0.0.1
```

## 9 实训遇到的问题与解决方案

实训过程中真正花时间的往往不是业务代码，而是环境、工具链和"看着对但其实不对"的问题。下面这些是我在实际操作中遇到并解决的，按现象、原因、处理三列列出，便于以后复现时少走弯路。

**表 20 实训问题与解决方案**

| 现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| 端口冲突：服务起不来 | 8080 被其他进程占用 | 改用 APP_PORT=18080 联调，前端代理目标同步指向新端口 |
| 登录行为在日志里查不到 | 中间件执行时用户尚未鉴权，拿不到身份 | 在业务层显式调用 recordLogin，成功与失败都落一条日志 |
| 授权提交非法权限点返回 500 | 非法 perm_id 直接写库触发外键约束 | 授权前校验权限点是否存在，非法返回 40001，事务仍回滚 |
| 删除部门后同编码无法新增 | 软删除行仍占唯一索引 | 删除改为物理删除，新增兜底把唯一键冲突映射为 409 |
| PowerShell 执行 Python heredoc 报错 | pwsh 不支持 << 语法，双引号内含中文引号也会解析失败 | 把编排逻辑写进任务专属 .py 文件，用 python 文件名 执行 |
| Git 远程仓库非空导致推送被拒 | 本地与远程历史无共同祖先 | 用 git merge --allow-unrelated-histories 合并一次，再正常推送，从不 force push |
| GitHub 推送频繁 Connection reset | 跨网络连接不稳定 | 改用 http.version=HTTP/1.1 + 固定间隔重试；以 fetch 后比对 commit hash 为成功判据 |
| 中文路径下的命令找不到文件 | PowerShell 把方括号等字符当通配符 | 改用 -LiteralPath，并避免在命令行里直接拼中文路径 |
| 令牌过期后页面停在原地 | 前端只提示错误，没有清理登录态 | 拦截器遇到 40100 清本地令牌并跳回登录页，带回原地址 |
| 刷新 /users 出现 404 | 单页应用未配置回退 | 发布端配置回退到 index.html（Nginx 用 try_files） |

这些问题里有两个对我触动最大。第一个是"测试预期写错"：12 条用例失败其实全是脚本预期码写错，如果不核对契约就直接改代码，很可能把本来正确的逻辑改坏，所以先确认"以谁为准"比闷头改更重要。第二个是"软删除与唯一索引的冲突"：概念上都懂软删除，但直到真的出现 500 才意识到删除标记会让唯一索引一直占位，最后按"基础配置数据物理删除"的方式解决，并把结论写进文档。

## 10 实训总结体会

六周下来，我最大的变化是从"能写出一段能跑的代码"变成"能交付一套能讲清、能验证、能重新部署的系统"。以前写作业只看功能跑不跑得通，这次每个模块都要回答：接口返回是否统一、失败时数据库是否一致、权限是不是在接口层拦住的、别人拿到的代码能不能直接编译运行。这四个问题一直推着我去补齐细节，而细节正是工程和练习的区别。

技术上收获最直接的是三层：数据库这一层，我第一次完整走完概念设计、逻辑设计到物理建表，体会到索引、外键与唯一约束并不是"加上去显得专业"，而是会在删除、重复提交这类场景里起作用；后端这一层，理解了 Gin 的中间件顺序、GORM 的事务边界与统一错误码的价值——这三样东西在联调和测试阶段省了大量沟通成本；前端这一层，从只会写单个组件到能组织布局、路由、请求封装与图表自适应，尤其是"统一在拦截器里处理登录失效"，比在每个页面各写一遍要可靠得多。

工程习惯上的收获可能比技术更长远。Git 从"随手提交"变成按模块提交、写清动因；遇到推送失败先 fetch 比 hash，确认到底是没推上去还是"看起来推上去了"；文档从最后补写变成边做边写，因为很多结论过一周就忘了为什么这么做。还有一点：把命令写进脚本而不是每次手敲，能复现的操作才叫验证过的操作。

测试视角也建立起来了。做接口测试的 48 条用例让我发现，负向用例比正向用例更容易暴露设计漏洞：非法权限点、非法层级、重复编码这类输入，往往在业务层没校验，直接落到数据库约束上变成 500。而我今后的就业方向是软件测试，这段经历让我更能理解"缺陷不是代码偶然写错，而是校验缺位"这句话。

不足也很清楚：缺少 Go 单元测试，测试全部停留在接口层；并发与性能没有验证，慢查询只做了字段索引，没有量化对比；数据权限只做了功能权限，data_scope 还是预留字段；前端还有部门管理、参数配置、日志查询三个页面未完成，这些都是下一步要补的。如果重做一次，我会在写完第一个接口时就同步补上单测与文档，而不是留到最后集中处理。

最后，这次实训让我对"工业软件支持企业数字化运营"有了具体的认识：它不是一个抽象口号，而是账号、组织、授权、配置、日志、指标这些细碎但必须准确的东西叠起来的结果。把每一件小事做到可验证，系统才立得住。
