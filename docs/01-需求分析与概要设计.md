# 基于工业软件企业后台管理系统数字化运营的需求分析与概要设计文档

工业软件开发综合实训（课程代码 192434303）· 2024级工业软件开发技术 · 文档版本 V1.0

## 1  项目概述

### 1.1  项目背景

工业软件企业承接的多为设备联网、生产执行、质量追溯类项目。项目交付之后，企业自身的账号、组织、授权、配置与运营指标往往分散在多个工具和台账中：账号由个人维护，授权靠口头约定，配置改动没有记录，运营情况靠人工统计。这种状态在人员流动和客户验收时容易暴露问题——谁在什么时间改了什么，某个部门能看到哪些数据，都难以追溯。把上述要素收敛到一个统一的 Web 后台，是企业从项目交付转向可持续运营的前提。

本项目是工业软件开发综合实训（课程代码 192434303，156 学时）的实践载体。实训要求在授权的开发环境中，独立完成基于 B/S 架构的企业后台管理系统的需求分析、设计、编码、测试与部署，掌握 Go 语言（Gin 加 GORM）后端开发与 Vue 3 前端开发的基本方法，理解前后端分离架构与 RESTful 接口规范，并规范使用 Git 完成版本管理。本文档是该项目的需求分析与概要设计成果，作为后续数据库设计、接口设计与编码实现的依据。

### 1.2  项目定位与建设范围

系统定位为企业内部数字化运营的后台支撑平台，服务对象是企业内部员工，不面向外部客户，也不承载生产设备的数据采集。系统以账号体系为入口、以 RBAC 为授权内核、以组织架构为归属维度、以参数配置为运行调节手段、以操作日志为审计底座、以运营看板为决策视图，六个部分互为支撑。为控制实训周期内的交付风险，建设范围按表1 划定边界。

## 2  业务目标

### 2.1  总体目标

建设一套可运行、可演示、可复核的企业后台管理系统，把“人（账号与组织）、权（角色与权限）、事（配置与审计）、数（运营指标）”四类要素集中到同一入口，实现统一的身份认证、统一的授权口径、统一的操作留痕与统一的运营视图。系统在实训周期内完成从环境确认、需求分析、设计、编码、联调、测试到部署的完整闭环，编译产物可通过浏览器访问并跑通核心业务流程。

### 2.3  业务价值与实施约束

从业务角度看，系统带来三点改变。一是授权维护从逐人配置变为按角色授权，新增员工只需挂接角色即可获得相应权限；二是登录、授权、配置变更等关键操作形成可检索的记录，审计有据可查；三是运营指标从人工汇总变为看板直读，部门与角色的分布、活跃趋势可以按时间范围观察。

实施约束有四条。开发周期 6 周，自 10 月中旬至 11 月下旬，单人开发；部署环境为本地机器或学校提供的服务器，不引入 Redis、消息队列等外部中间件；数据为构造的测试数据，不接入任何生产系统；开发机需同时满足 Go 1.25、Node.js 16 及以上与 MySQL 8.0 的运行条件。约束直接影响架构选择：单体后端加静态前端、配置走内存缓存、统计走 SQL 聚合，都是在这一约束下的合理取舍。

### 3.2  登录与用户管理

登录是系统的唯一入口。用户以账号与口令登录，后端校验通过后签发 JWT，前端在后续请求的鉴权头中携带该令牌，后端中间件解析令牌并注入当前用户上下文。用户是后台的身份载体，每个用户绑定一个主部门，并可挂接多个角色；用户的启停状态直接决定其令牌是否继续可用，因此停用即等于即时下线。

**业务规则：**（1）账号全局唯一，长度 4 至 20 位，以字母开头，允许字母、数字与下划线；姓名、部门、角色为新增时的必填项。（2）口令长度不少于 8 位且同时包含字母与数字，入库前使用 bcrypt（cost 10）加盐哈希，数据库中不得出现明文口令，任何接口与日志均不输出口令字段。（3）同一账号连续 5 次登录失败锁定 10 分钟，锁定期间返回明确提示，但不区分账号不存在与口令错误，避免账号枚举。（4）令牌有效期 2 小时，载荷包含用户标识、角色标识与过期时间，签名密钥由环境变量注入，不写入代码仓库。（5）用户创建在同一事务内完成插入用户与写入用户角色关联两步，任一步失败整体回滚。（6）删除用户采用软删除，仅标记删除时间并置为停用，避免历史日志失去操作主体。（7）新增与编辑共用一套参数校验规则，前端即时提示，后端最终校验，两侧规则一致。

**接口约定：**服务端对入参做类型与长度校验，口令类字段不进入任何日志。用户列表默认按创建时间倒序，每页 20 条，单页上限 50 条。列表返回的字段中，口令哈希与内部状态标识不向前端输出。

### 3.3  角色与权限管理

权限模型采用 RBAC，即用户、角色、权限三级关联：用户不直接持有权限，而是通过角色获得权限集合；一个用户可挂接多个角色，其有效权限为各角色权限的并集。角色是授权的管理单元，权限点是授权的最小粒度，按菜单、按钮、接口三类组织成树，权限点编码采用模块冒号动作的格式，例如 user:create、role:grant，与后端路由组和前端的按钮显隐一一对应。

**业务规则：**（1）角色名称与角色编码唯一，角色需声明数据范围，本期统一为全部范围。（2）超级管理员为内置角色，不可删除、不可取消授权，用于权限兜底。（3）删除角色前先校验是否被用户引用，被引用时拒绝删除并返回引用数量。（4）角色授权在事务内完成：先按角色清空旧关联，再批量写入新关联，避免出现半授权的中间状态，具体流程见 5.4 节图3。（5）权限校验在每次请求时实时比对，授权变更后无需重新登录即生效；校验失败返回 403 并记录一条越权访问日志。（6）前端菜单与按钮按权限点渲染，但这只作体验优化，真正的拦截必须在后端完成。

权限点维护属于 P1 功能。若开发周期紧张，可先以内置权限点表配合 SQL 初始化脚本替代可视化的维护页面，授权与校验链路不受影响，后续再补页面。

### 3.4  部门与组织架构管理

部门采用单表自关联的树形结构，通过上级标识指向上级部门，配合层级字段与排序号，支持三级及以上组织深度。部门同时是统计维度：用户列表、看板分布、日志检索都可按部门过滤，因此部门数据必须保持完整，不允许出现没有上级的孤儿节点。

**业务规则：**（1）同级部门名称唯一，不同层级允许重名。（2）新增部门必须指定上级，根部门固定为总公司，不可删除。（3）部门删除前校验子部门与成员，任一项存在则拒绝，并提示具体数量。（4）部门负责人可为空；若指定，必须是状态为启用的用户。（5）排序号用于同层展示顺序，修改后立即生效。（6）部门名称变更不影响其下用户与历史日志的关联，因为关联依据是部门标识而非名称。

### 3.5  系统参数配置

系统参数用于承载运行期可调整的策略，例如口令最小长度、登录失败锁定次数、令牌有效期、看板默认时间范围、日志保留天数。参数以键值对形式集中存放在配置表中，按基础、安全、业务、看板四类分组展示，避免散落在代码常量中。

**业务规则：**（1）参数键全局唯一，命名采用分类点名称的格式，例如 security.token.expire。（2）每个参数声明数据类型，取值类型限定为字符串、整数、布尔与 JSON，保存时按类型做格式校验，整数还需校验取值范围。（3）安全类参数的修改需二次确认，并在操作日志中记录修改前后的值。（4）参数在服务启动时加载至内存缓存，修改成功后刷新缓存，读取不落库，避免高频查询。（5）参数不可物理删除，只能停用；停用后业务代码回退到代码内默认值。（6）参数值不得包含数据库连接串、第三方密钥等敏感信息，此类配置通过环境变量注入。

### 3.6  运营数据看板

看板面向管理层与运营岗，用一屏回答四个问题：人有多少、活不活跃、在用什么、分布在哪些部门。数据全部由后端统计接口聚合返回，前端只做渲染，不在浏览器内做二次计算，以保证同一指标在不同页面口径一致。统计口径统一以服务器时间为准，按自然日切分，具体指标定义见表5。

**表5  运营看板指标口径**

| 编号 | 指标 | 统计口径 | 图表 | 粒度 |
| :--: | :--- | :--- | :--- | :--: |
| M-01 | 用户总数 | 用户表中未删除记录的计数 | 数字卡片 | 当前 |
| M-02 | 新增用户趋势 | 按创建日期分组计数，缺失日期补 0 | 折线图 | 日 / 周 |

### 3.7  操作日志管理

日志是系统的审计底座。除登录与退出外，用户增删改、角色授权、部门变更、参数修改等关键操作均由中间件在响应返回后落库，记录操作人、模块、动作、请求方法、请求地址、客户端地址、耗时、结果与操作时间。日志写入不阻断业务：写库失败只记录到服务端错误日志，不影响接口正常返回。

**业务规则：**（1）日志字段中不得包含口令、令牌、证件号等敏感内容，请求参数按白名单方式记录关键字段。（2）日志保留 180 天，超期由手工清理脚本处理，本期不做自动归档。（3）查询默认近 7 天，支持操作人、模块、结果、时间范围与关键字五个条件组合，每页 20 条。（4）日志表按时间字段建索引并对模块建组合索引，保证十万行量级下的查询响应。（5）越权访问单独记录一条日志，便于发现异常探测行为。（6）日志详情只读，任何角色均无删除权限。

## 4  非功能性需求

### 4.1  安全需求

安全需求围绕四点展开：进得来要认证可靠，看得住要授权精确，改不了要防注入与防越权，查得到要留痕完整。表6 列出九项安全要求及对应的实现措施，措施与第 8 章的技术选型相互对应。

**表6  安全需求**

| 编号 | 安全要求 | 实现措施 | 验证方式 |
| :--: | :--- | :--- | :--- |
| S-01 | 口令安全存储 | bcrypt（cost=10）加盐哈希，库中无明文，接口与日志不输出口令 | 查库核对哈希值，检索日志确认无口令字段 |
| S-02 | 身份认证 | 登录签发 JWT（HS256，2 h 过期），密钥由环境变量注入 | 以过期令牌与伪造令牌请求，均返回 401 |
| S-03 | 访问控制 | RBAC 中间件接口级鉴权，权限点与路由组一一对应 | 越权矩阵测试，返回 403 并落越权日志 |
| S-04 | SQL 注入防护 | GORM 参数化查询，禁止拼接 SQL，排序字段走白名单 | 注入 OR 1=1 类载荷，返回结果不异常 |
| S-05 | 会话与状态 | 停用用户即时失效，令牌过期需重新登录 | 停用账号后携原令牌请求，返回 401 |
| S-06 | 敏感信息处理 | 日志按白名单记录参数，配置中不放密钥与连接串 | 检查日志内容与仓库配置文件 |
| S-07 | 传输与跨域 | CORS 白名单限定来源，部署环境启用 HTTPS | 非白名单来源被拒，HTTPS 访问正常 |
| S-08 | 审计留痕 | 登录、授权、配置变更、用户增删全部落库 | 执行操作后检索日志核对 |
| S-09 | 错误处理 | 统一错误码，不返回堆栈与 SQL 语句 | 构造异常请求，检查响应体内容 |

除表中措施外，还需遵守三条工程纪律：代码仓库中不提交任何明文口令、密钥与数据库连接串，统一通过环境变量或本地配置文件注入并写入忽略清单；接口错误响应只返回业务错误码与可读提示，不返回堆栈与 SQL 语句；演示与验收前清理测试账号与调试接口。

### 4.2  性能需求

性能目标按单人使用、内网访问、十万行数据的场景设定，重点保证列表与统计类接口的响应，而不是追求高并发。表7 给出指标、测量条件与保障措施。

**表7  性能需求**

| 指标项 | 目标值 | 测量条件 | 保障措施 |
| :--- | :--: | :--- | :--- |
| 登录接口响应 | P95 ≤ 300 ms | 20 并发、连续 100 次请求 | bcrypt 比对加两次索引查询，不出现全表扫描 |

### 4.4  其他约束

可维护性方面，后端按控制器、服务、仓储三层组织，跨层调用只允许自上而下；前端按页面、组件、接口三层组织，所有请求收敛在统一的接口目录。可靠性方面，服务启动时打印数据库连接与监听端口信息，关键失败有明确日志；数据库连接池显式设置最大打开与最大空闲连接数，避免连接耗尽。易用性方面，界面统一使用 Element Plus 组件与统一间距，表单错误提示定位到具体字段，列表的空态、加载态与错误态齐备。

## 5  系统架构

### 5.1  架构风格

系统采用前后端分离的 B/S 架构。浏览器端是 Vue 3 构建的单页应用，编译后为静态资源，由 Nginx 或 Go 服务托管；服务端是 Gin 构建的 RESTful 接口服务，只返回 JSON，不渲染页面；两端通过 HTTP 上的 JSON 数据交互，以 JWT 承载身份，服务端不保存会话。后端内部按 MVC 思路分为路由、控制器、服务、仓储四段，依赖方向单向：前端依赖接口，接口依赖服务，服务依赖仓储，仓储依赖数据库，反向依赖一律禁止。

### 5.2  总体架构

图1 以文字方式给出系统的分层结构，箭头表示调用方向与数据流向。

```text
用户层    企业管理员 · 部门主管 · 运营专员 · 审计员（浏览器访问）
             │ HTTP / HTTPS
             ▼
接入层    Nginx 静态资源托管 + /api 反向代理（本地演示由 Gin 直接托管）
             │
             ▼
表现层    Vue 3 单页应用：登录页 · 首页 · 用户/角色/部门/配置管理页
          · 运营数据看板 · 操作日志页
          组件：Element Plus · Axios · ECharts · Vue Router
             │ RESTful JSON + JWT（Authorization: Bearer）
             ▼
接入过滤  Gin Engine 路由分组 /api/v1 + 中间件链
          日志 → 恢复 → 跨域 → 鉴权(JWT) → 权限(RBAC) → 操作留痕
             │
             ▼
应用层    Controller（参数绑定与校验、统一响应封装）
          Service（业务规则、事务边界、统计聚合）
          Repository（GORM 模型、查询构造、预编译语句）
             │ GORM 连接池 / 参数化 SQL
             ▼
数据层    MySQL 8.0（InnoDB · utf8mb4）
          用户 · 角色 · 权限 · 用户角色 · 角色权限 · 部门 · 系统配置 · 操作日志
```

图中五层职责清晰：表现层只负责交互与展示，不承载业务规则；接入层负责协议、跨域与中间件编排；应用层承载业务规则与事务边界；数据层保证持久化与一致性。鉴权与权限判定前置于业务处理，意味着任何业务接口在进入控制器之前就已完成身份与权限校验，业务代码无需重复判断。

各层的职责边界与关键实现见表9。划分依据是变更频率：越靠上的层变更越频繁，越靠下的层越稳定，把频繁变化的部分隔离在上层，可以降低改动影响面。

| 表现层 | 页面渲染、表单交互、图表展示、请求封装 | Vue 3、Element Plus、Axios、ECharts |

### 5.4  关键流程

登录与鉴权是系统的主流程，图2 描述从表单提交到令牌生效的全过程，其中的每一步都对应一个可测试的检查点。

```text
① 浏览器：输入账号与口令 → 前端非空与长度校验
        │ POST /api/v1/auth/login
        ▼
② Gin 路由 → 参数绑定校验 → AuthService
        │
        ▼
③ 按账号查询用户（预编译）→ 校验账号状态（启用 / 停用）
        │
        ▼
④ bcrypt 比对口令哈希 → 成功则重置失败计数；失败则累计并判断锁定
        │
        ▼
⑤ 查询用户角色与权限集合 → 签发 JWT（HS256，有效期 2 h）
        │
        ▼
⑥ 返回 {code:0, data:{token, user, menus, perms}} → 前端存储并跳转首页
        │
        ▼
⑦ 后续请求头 Authorization: Bearer <token>
   → 鉴权中间件（签名、过期时间、用户状态）
   → 权限中间件（角色→权限点，比对当前路由）
   → 业务 Handler → 操作留痕 → 统一响应
```

### 5.6  数据模型概要

数据库采用 InnoDB 引擎与 utf8mb4 字符集，共设计八张核心表，表12 列出表名、用途与关键约束。字段级设计、索引与初始化数据见《数据库设计说明书》。

| :--: | :--- | :--- | :--- |
| sys_user | 用户主表 | id、username、password_hash、real_name、dept_id、status、created_at | username 唯一；dept_id 索引 |
| sys_role | 角色表 | id、role_name、role_code、data_scope、remark | role_code 唯一 |
| sys_permission | 权限点表 | id、parent_id、perm_name、perm_code、perm_type | perm_code 唯一；parent_id 自关联 |
| sys_user_role | 用户角色关联 | user_id、role_id、created_at | 联合唯一（user_id, role_id） |
| sys_role_permission | 角色权限关联 | role_id、perm_id | 联合唯一（role_id, perm_id） |
| sys_dept | 部门表 | id、parent_id、dept_name、leader_id、sort_no、status | parent_id 自关联；同级名称由业务校验 |
| sys_config | 系统配置表 | id、config_key、config_value、value_type、category、status | config_key 唯一 |
| sys_oper_log | 操作日志表 | id、user_id、module、action、method、url、ip、cost_ms、result、created_at | created_at 索引；（created_at, module）组合索引 |

**实体关系：**一个部门包含多个用户，部门自身通过上级标识形成树；一个用户可拥有多个角色，一个角色可分配给多个用户，二者通过用户角色关联表连接；一个角色包含多个权限点，一个权限点可属于多个角色，二者通过角色权限关联表连接；一个用户产生多条操作日志，日志通过用户标识关联而不设外键，以降低高频写入的开销。

**范式与事务：**表结构按第三范式组织，用户表不冗余存储角色名称与部门名称，避免更新异常；关联表只保存两个外键与必要的审计字段。涉及一致性的操作集中在三处并显式使用事务：用户创建与角色写入、角色授权、部门成员批量调整。日志类写入不参与业务事务，避免长事务拖慢主流程。

### 7.3  关键用例详述

选取三个链路最长、风险最高的用例做详细描述，其余用例按同一模板在接口文档中展开，模板统一为前置条件、基本流与异常流三段。

#### 7.3.1  登录认证（UC-01）

**前置条件：**用户已开通账号且状态为启用；服务端可访问数据库。

**基本流：**（1）用户在登录页输入账号与口令，前端做非空与长度校验后提交。（2）后端校验参数格式，按账号查询用户记录。（3）比对口令哈希，成功后重置失败计数。（4）签发令牌，查询用户角色与权限集合。（5）返回令牌、用户信息与菜单树，前端写入本地存储并跳转首页。

**异常流：**（1）账号不存在或口令错误，累计失败计数并返回统一提示；（2）账号被停用，返回账号已停用的提示；（3）连续失败达 5 次，锁定 10 分钟；（4）令牌过期后访问业务接口，返回未登录错误码，前端清除本地令牌并跳转登录页。

#### 7.3.2  角色授权（UC-04）

**前置条件：**操作者具备授权权限；目标角色存在且非内置角色。

**基本流：**（1）进入角色列表，选择目标角色打开授权面板。（2）前端按权限点树渲染勾选状态，回显该角色已有权限。（3）提交后进入事务：清空该角色旧关联、批量插入新关联、提交。（4）写入一条授权操作日志并返回成功。

**异常流：**（1）权限点标识非法，事务回滚并返回参数错误；（2）目标角色为超级管理员，直接拒绝；（3）并发授权同一角色，后提交者覆盖前者，前端提示刷新后核对结果。

#### 7.3.3  查看运营看板（UC-08）

**前置条件：**操作者具备看板查看权限；统计接口可访问。

**基本流：**（1）进入看板页，默认加载近 7 天数据。（2）后端一次聚合返回概览、趋势、分布三组数据。（3）前端渲染数字卡片、折线图、柱状图与环形图。（4）用户切换时间范围为近 30 天，重新请求并重绘。

**异常流：**（1）统计接口超时，卡片显示加载失败并可点击重试；（2）数据为空，展示空态占位而不报错；（3）图表容器宽度变化，触发自适应重绘。

### 8.2  后端技术

**Go 1.25：**选择 Go 作为后端语言，主要看重三点。一是静态编译，go build 产出单一可执行文件，不依赖运行时环境，部署时只需拷贝文件与配置，与实训的服务器条件匹配；二是并发模型简洁，通道与轻量线程让并发任务的处理直观，标准库已能满足 HTTP 服务需要；三是工程约束强，未使用的变量、未处理的错误都会导致编译失败，这在单人开发中反而降低了低级错误。Go 1.25 在标准库与工具链上进一步稳定，可作为长期基线版本。

**Gin：**Gin 承担 HTTP 层，价值在于路由分组与中间件链。把统一前缀下的路由按模块分组，将日志、恢复、跨域、鉴权、权限、操作留痕依次挂为中间件，业务处理器只处理业务，横切逻辑集中在中间件，新增一个受保护接口只需挂到对应分组。参数绑定与校验通过结构体标签完成，减少手写判断。

**GORM：**GORM 承担持久层。结构体与表字段映射，查询以链式条件构造并默认参数化，从源头降低注入风险；事务通过回调形式提交，配合连接池配置可控制并发压力；关联查询支持预加载，避免逐条查询。需要说明的是，自动迁移只用于开发阶段同步表结构，正式交付以 SQL 脚本建表，避免迁移结果不可控。

**分层与统一封装：**后端按控制器、服务、仓储分层：控制器只做参数绑定、调用服务、封装响应；服务承载业务规则与事务边界；仓储封装数据访问。统一响应结构、全局异常恢复与错误码集中定义在公共包中，供各模块复用，保证所有接口返回格式一致。

### 8.3  数据库

选择 MySQL 8.0，一是课程与任务书指定，二是它在本次场景下能力匹配：InnoDB 提供事务与行级锁，满足用户创建与角色授权的一致性要求；utf8mb4 完整支持中文，避免乱码；8.0 的窗口函数与公用表表达式使趋势统计、占比计算可直接在 SQL 内完成，不必把聚合搬到应用层；JSON 类型可用于存放结构化的参数值。索引方面，按查询路径为高频条件建普通索引与组合索引，唯一约束用于账号、角色编码、参数键等业务唯一字段；核心表保留外键以维持参照完整性，日志表刻意不建外键以换取写入性能。

### 8.4  前端技术

**Vue 3 与 Element Plus：**前端采用组合式 API，页面以单文件组件组织，逻辑集中在 setup 中，配合响应式引用驱动视图；构建工具使用 Vite，开发期热更新快，生产期按路由分包。Element Plus 提供表格、表单、树、分页、弹窗等后台常用组件，设计语言统一，能显著压缩界面开发时间；本项目以它为唯一组件库，避免多套组件混用导致风格分裂。权限控制上，路由守卫校验登录态，菜单与按钮按权限点渲染。

**Axios 与 ECharts：**Axios 通过请求与响应拦截器统一处理三件事：请求头注入令牌、响应统一解包业务码与提示、未登录与越权集中跳转或提示，业务代码因此只需关心数据本身。ECharts 负责看板可视化，折线图表达趋势，柱状图表达频次，环形图与饼图表达占比分布；采用按需引入，只注册实际使用的图表类型与组件，控制打包体积；容器尺寸变化时调用重绘，保证不同分辨率下不变形。

### 8.5  安全与版本管理

**JWT：**鉴权采用 JWT 而非服务端会话，原因是服务端无状态、易于部署与横向扩展，且令牌自带过期时间。实施要点有三：签名算法使用 HS256，密钥由环境变量注入；载荷只放用户标识、角色标识与过期时间，不放敏感信息；每次请求校验签名、过期时间与用户状态，用户被停用即令牌失效。JWT 无法主动吊销的短板，通过短有效期与状态校验共同弥补。

**Git 与 GitHub：**版本管理采用 Git，仓库托管在 GitHub，按学校要求也可换用 Gitee。分支模型为：主分支保留可运行版本，集成分支用于日常合并，功能分支按模块命名；功能完成并自测后合并回集成分支，阶段验收后合并主分支。提交信息采用类型加简述的格式，类型取 feat、fix、docs、refactor、test、chore 之一，一次提交只做一件事，便于回溯。修改数据库结构或核心代码前先提交一次备份点，这是任务书明确要求的操作纪律。仓库需包含说明文件交代环境要求、启动步骤与默认账号，并通过忽略清单排除编译产物、依赖目录与本地配置。

### 8.6  选型权衡与风险

任何选型都有代价，表17 列出主要风险与应对措施，这些应对措施需要在开发阶段逐项落实，而不是验收前临时补救。

**表17  选型风险与应对**

| 风险点 | 影响 | 应对措施 |
| :--- | :--- | :--- |
| JWT 无法主动吊销 | 用户停用后旧令牌短期仍有效 | 每次请求校验用户状态；有效期压至 2 h |
| GORM 自动迁移 | 表结构与脚本不一致，交付环境不可控 | 仅开发期使用，交付以 SQL 脚本建表 |
| 统计数据量增长 | 聚合变慢，看板超时 | 时间字段建索引，限定时间范围，必要时预聚合 |
| ECharts 打包体积 | 首屏加载变慢 | 按需引入图表与组件，路由分包异步加载 |
| 单体部署扩展性 | 并发升高时单进程成为瓶颈 | 接口无状态、连接池可控，后续可加进程或拆分 |
