# 基于工业软件企业后台管理系统数字化运营

项目部署与运行说明（第 14 章）

## 1 部署概述

### 1.1 部署目标与部署形态

本章说明如何把"基于工业软件企业后台管理系统数字化运营"项目从源码变成可在本机直接运行的两部分：Go 后端编译出的单个可执行文件，以及 Vue 前端打包出的静态资源目录。部署形态为单机部署——后端进程监听 HTTP 端口提供 /api/v1 接口，前端静态资源由一个轻量服务发布并把 /api 前缀的请求转发给后端，浏览器访问前端地址即可使用系统。项目不依赖容器与云服务，答辩机房一台装有 MySQL 的 Windows 机器即可复现。

本章的每条命令与每个结果均在本机实际执行过：后端编译产物 20.1 MB，前端打包产出 16 个文件、合计约 2.44 MB，打包产物通过 4173 端口发布后经代理调用登录接口返回 HTTP 200、code=0。文中出现的体积、耗时、日志片段都是这次实际运行的结果，不是估算。

### 1.2 环境要求

**表 1 环境要求**

### 1.3 部署流程总览

整体顺序是"先建库、再编译后端、再打包前端、最后启动并验收"。四步之间有两处强依赖：后端启动前数据库必须已导入 SQL 脚本，否则进程会在初始化连接时直接退出并打印"数据库初始化失败"；前端打包虽不依赖后端运行，但打包产物里的接口请求地址固定为相对路径 /api/v1，因此发布前端时必须配一层代理，否则登录页会提示网络异常。流程与产出见表 2。

**表 2 部署流程与每步产出**

| 步骤 | 操作 | 关键命令 | 产出 |
| :--: | :--- | :--- | :--- |
| 1 | 导入数据库脚本 | mysql < industrial_admin.sql | 库表与种子数据 |
| 2 | 后端依赖与编译 | go mod tidy、go build | industrial_admin.exe |
| 3 | 前端依赖与打包 | npm install、npm run build | web/dist 静态目录 |
| 4 | 启动后端与前端 | 运行 exe、发布 dist 并配代理 | 可访问的登录地址 |
| 5 | 验收 | 登录、看板、用户列表 | 部署完成确认 |

## 2 Go 后端编译为可执行文件

### 2.1 拉取依赖

进入后端根目录（与 main.go、go.mod 同级），先确认依赖完整。首次在新机器上编译时执行 go mod tidy，它会按 go.mod 下载 Gin、GORM、MySQL 驱动、JWT 等依赖并回写 go.sum；网络受限时先设置代理。

```text
go mod verify      # 校验依赖包哈希与 go.sum 是否一致
```

### 2.2 执行编译

### 3.3 产物结构与发布方式

**表 5 前端打包产物说明**

| 路径 | 内容 | 说明 |
| :--- | :--: | :--- |
| dist/index.html | 入口页面 | 引入打包后的 js/css，单页应用只有这一个入口 |

### 3.4 打包注意事项

第一，含敏感信息的配置不要写进前端代码。前端任何变量都会被打进 js 文件，浏览器可直接查看，因此数据库口令、JWT 密钥一律只放在后端的运行环境变量里。第二，代理地址不要硬编码：vite.config.js 中的代理目标已支持 PROXY_TARGET 环境变量覆盖，换后端端口时只改变量。第三，打包前先关注控制台告警，本项目在前端联调阶段已消除业务告警，仅剩 favicon 404 这类资源提示。

### 4.3 发布前端并配置代理

前端 dist 需要由一个静态服务发布，并把它收到的 /api 请求转发给后端。本项目实际验证过的两种方式如下，两者都无需修改前端源码。

**方式一：**使用 Vite 自带的 preview 服务发布 dist。它默认继承 vite.config.js 的代理配置，因此只需把 PROXY_TARGET 指向正在运行的后端，即可在 4173 端口访问打包后的真实产物。本机实测：首页返回 200，经该服务代理请求 /api/v1/auth/login 返回 200、code=0，说明打包产物与后端已打通。

```text
cd web
$env:PROXY_TARGET = "http://127.0.0.1:18080"

# 发布 dist 到 4173 端口
npx vite preview --port 4173 --host 127.0.0.1

# 浏览器访问 http://127.0.0.1:4173/ ，用管理员账号登录
```

代码 10 用 preview 发布 dist（打包验收与答辩演示推荐）

**方式二：**使用 Nginx 同时承担静态发布与反向代理，适合长期运行。把 dist 拷到 Nginx 的 html 目录，用如下配置实现"静态回退 + 接口转发"，前端与后端共用一个端口，浏览器不会产生跨域。

```text
server {
    listen       80;
    server_name  localhost;

    # 前端静态资源：单页应用，找不到文件时回退 index.html
    root   html/industrial_admin;
    index  index.html;
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 接口反向代理：把 /api 原样转发给 Go 后端
    location /api/ {
        proxy_pass         http://127.0.0.1:18080;
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
    }
}
```

### 4.5 停止服务

前端 preview 进程直接关闭窗口或用 Stop-Process 结束；后端在控制台按 Ctrl+C，程序会先停止接收新请求、等待在途请求结束（最长 5 秒）再关闭连接池并打印"服务已退出"，不建议直接结束进程。若日志文件被进程占用，需先停止进程再删除，否则会报文件被占用。

## 6 敏感信息处理与安全检查

### 6.1 口令与密钥的处理方式

项目在代码层面做了三点约束：一是数据库口令、JWT 密钥只从环境变量读取，源码中没有硬编码的口令；二是用户口令一律经 bcrypt 加盐哈希后入库，表字段注释与建表脚本都写明"禁止存明文"，登录与日志均不输出口令；三是 .env 文件被 .gitignore 排除，仓库只保留不含真实口令的 .env.example 模板，其中 DB_PASSWORD 一项刻意留空。

### 6.2 交付前的检查结果

对当前仓库做了一次针对敏感信息的检索，结果与处理方式见表 8。整体结论：源码与仓库中不含数据库口令；存在一处开发期默认密钥与两个演示账号，需在部署前替换与清理。

**表 8 敏感信息检查结果**

| 检查对象 | 位置 | 发现 | 处理方式 |
| :--- | :--- | :--- | :--- |
| 数据库口令 | 源码与 .env.example | 未发现硬编码，说明样例中该值为空 | 无需处理，部署时用环境变量传入 |
| JWT 密钥 | config/config.go | 存在开发兜底默认值 dev-only-secret-change-me | 部署必须用 JWT_SECRET 覆盖；建议同时把默认值改为空串并强制校验，避免忘记设置时静默使用弱密钥 |
| 种子账号口令 | sql/industrial_admin.sql 种子数据与哈希 | 脚本中仅存 bcrypt 哈希，注释不再写明文口令 | 交付前修改 admin 口令、删除 test01 或改其口令；哈希本身不是明文，可保留在脚本中用于演示 |
| 测试脚本账号 | tools/test_api_record.py | 含演示账号口令，用于接口回归 | 属教学演示数据，不应复用到生产；如需对外发布，改为从环境变量读取 |
| 构建产物 | 仓库根目录与 web 目录 | exe、dist、run_*.log 均未入库（.gitignore 已排除） | 交付时只打包 exe 与 dist，不提交本机日志与临时文件 |
| 跨域策略 | middleware/cors.go | 当前回显请求来源以方便联调 | 生产环境改为固定白名单域名 |

## 7 部署常见问题排查

下表汇总本机部署过程中实际遇到或可预期的故障现象与处理方式。排查顺序建议从后端日志开始，确认进程与数据库正常后再看前端，避免在代理层反复试错。

**表 10 部署常见问题**

| 现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| 启动即退出，日志"数据库初始化失败" | 库未建、口令错或 MySQL 服务未启动 | 先导入 SQL 脚本，再用 mysql 客户端手工连一次验证口令 |
| 端口被占用，listen tcp :8080 | 8080 被其他程序占用 | 换 APP_PORT=18080，并同步把前端 PROXY_TARGET 指向新端口 |
| 浏览器登录提示网络异常 | 前端未配代理，/api 请求打到了前端端口 | 按 4.3 节配置 preview 的 PROXY_TARGET 或 Nginx 的 /api 反代 |
| 刷新 /users 出现 404 | 单页应用未配置回退 | Nginx 加 try_files $uri $uri/ /index.html |
| 登录返回 401/40100 | 账号口令错或令牌过期（默认 2 小时） | 重新登录；排查时确认 Authorization 头为 Bearer 前缀 |
| 接口返回 403/40300 | 账号权限点不足 | 用 admin 验证；普通账号需先在角色授权页分配权限点 |
| 日志文件删不掉 | 进程仍占用文件句柄 | 先 Stop-Process 停止进程，再删除日志 |
| 前端打包提示分块超过 500 kB | ECharts 整包引入 | 不影响运行；如需优化改为按需引入 echarts 组件 |

## 8 部署结论

按本章步骤，项目可由源码复现为一套可运行的本地系统：后端单个 exe 在 18080 端口提供 25 个接口，前端 dist 经 4173 端口发布并通过代理访问后端，浏览器登录后可正常进入运营看板、用户管理与角色授权页面。编译与打包过程无错误，仅有 ECharts 分块体积告警，属可优化项。

部署阶段验证了三条关键工程约束：配置与密钥不外置到代码；前端不含任何密钥类常量；产物与日志不入库。需要改进的两处已在表 8 中列明——JWT_SECRET 的开发兜底默认值应在代码中改为空并强制校验，演示账号应在交付前更换口令或清理。上述两项与接口测试记录中提出的缺陷一同列入后续改进清单。
