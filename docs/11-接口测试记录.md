# 基于工业软件企业后台管理系统数字化运营

接口测试记录表（第 13 章）

## 1 测试概述

### 1.1 测试目的

本记录对应《工业软件开发综合实训》（课程代码 192434303）任务书"要求 7"中的第 4 项提交物"测试记录"，针对"基于工业软件企业后台管理系统数字化运营"项目已完成的后端接口做功能性验证。测试要回答三个问题：接口在正常输入下能否返回符合统一格式约定的数据；在非法输入、越权访问、数据冲突等异常情形下能否给出明确可解释的错误码而不是崩溃；关键写操作失败后数据库是否保持在一致状态。

测试对象为 Go 1.25 + Gin + GORM 实现的后端服务，共 6 个功能模块、48 条用例。所有"实际结果"均为在本机真实运行的服务上逐条发送 HTTP 请求后记录的返回内容，不是设计推演；记录表下方的缺陷小节列出了本轮测试中发现并已修复的两个问题。

### 1.2 测试范围与用例分布

测试范围覆盖任务书要求的登录、用户管理、角色授权、部门管理、日志查询、统计看板 6 个模块。除正向功能用例外，每个写操作模块都补充了参数校验、权限不足、数据重复与数据不存在等负向用例，并针对授权与部门树补充了"失败后回查数据库"的一致性校验用例。用例分布见表 1。

### 1.3 测试依据与判定标准

判定依据是项目已固化的三点约定：一是统一返回体 {code, message, data}，code=0 表示业务成功；二是错误码字典 CodeSuccess=0、CodeParamInvalid=40001、CodeUnauthorized=40100、CodeForbidden=40300、CodeNotFound=40400、CodeConflict=40900、CodeServerError=50000，并由 HTTPStatus() 映射为 200/400/401/403/404/409/500；三是列表类接口统一返回 {list,total,page,pageSize}。

一条用例判为"通过"需同时满足：HTTP 状态码与业务码符合上述字典、message 能说明失败原因、返回结构与约定一致；涉及写操作的用例还要在请求后回查一次，确认数据库状态符合预期。任一项不符即判为"未通过"并登记为缺陷。

## 5 覆盖情况说明

已覆盖：6 个模块的全部对外接口在正常输入下的返回结构；登录的口令错误、账号不存在、空账号、超长账号；用户模块的重复账号、缺必填项、内置管理员禁删、删除后回查；角色模块的内置角色禁改、非法权限点、整体替换后回查；部门模块的编码重复、上级设为自身、成环、有子部门禁删；日志与统计模块的权限不足、统计窗口参数上限与非法值回落。

未覆盖，需在后续阶段补充：一是 Go 侧单元测试（项目当前没有任何 *_test.go，测试全部为接口级黑盒）；二是并发与压力场景，如两个管理员同时删除同一部门、批量授权时的竞态，本轮未构造并发请求；三是数据权限 data_scope 的实际过滤效果，当前只验证了功能权限（权限点）层面的拦截；四是浏览器端与 Postman 之间的差异（跨域、超时、断网重试），这部分在第 11、12 章的前端联调中另行验证；五是文件导入导出、消息通知等尚未实现的接口。上述边界在综合实训总结报告中作为改进方向提出。

## 7 Apifox 接口测试操作说明

Apifox 把"接口文档 + 调试 + 自动化测试 + Mock"放在同一个项目里，本项目的 6 个模块刚好可以按目录组织，答辩时既能看文档又能跑用例。以下步骤与 Postman 的用例一一对应。

### 7.1 项目与环境

新建项目（名称 工业后台管理系统），在"环境管理"里建"本地"环境：前置 URL 填 http://127.0.0.1:18080/api/v1，变量表新增 token、empToken 两个变量并设为"临时变量"。接口路径统一写相对路径 /auth/login、/users，前缀由环境拼接，切换部署环境时只改变量。

### 7.2 接口目录组织

按"登录鉴权 / 用户管理 / 角色授权 / 部门管理 / 日志查询 / 统计看板"建 6 个目录，把后端 25 个接口归到对应目录下。若后端已维护 OpenAPI 描述文件，可用"导入—OpenAPI/Swagger"一次性导入；否则用"手动新建"逐条录入，方法、路径、请求参数、返回示例按第 3 节的接口名称与输入填写，返回示例直接粘贴实际报文，Apifox 会据此生成文档。

### 7.3 设置鉴权与用例

在"目录—登录鉴权"下把 POST /auth/login 设为登录接口，并在项目设置的"鉴权"中选择 Bearer Token，值填 {{token}}；然后在登录接口的"后置操作"里添加"提取变量"：变量名 token、来源 JSONPath $.data.token。这样跑自动化时，登录接口执行完会把新令牌写回环境，其余接口自动带令牌。

每个接口下建"测试用例"，用例只覆盖差异字段（如非法 permIds、days=999），断言在"后置操作"里配置：校验 HTTP 状态码、校验 JSONPath $.code、校验 $.message 关键字。Apifox 的断言按"实际值 / 期望值"两列填写，不需要写脚本，这一点比 Postman 更适合写进实训报告的表格化记录。

### 7.4 自动化测试与报告

进入"自动化测试"新建测试场景，把 48 条用例按模块拖入步骤列表，设置"登录 → 其他模块"的顺序，用例间用"等待 200 ms"避免连续写库。点"运行"，Apifox 会给出通过率与每条用例的耗时；运行完成后可"导出报告"为 HTML 或 PDF，报告中包含请求、响应、断言结果三部分，可直接作为任务书第 5 项"操作与验收截图"的素材。若需要回归，把该场景加入"定时任务"即可按天执行。

### 7.5 与 Postman 的差异

**表 13 Postman 与 Apifox 的差异**

| 对比项 | Postman | Apifox |
| :--- | :--- | :--- |
| 文档与测试 | 需另写文档或用导出功能 | 接口即文档，同一份数据同时驱动调试与用例 |
| 断言方式 | 写 JavaScript（pm.test） | 表格化配置，也可写脚本，适合教学演示 |
| 鉴权串联 | Tests 里 set 环境变量 | 后置操作提取变量，配置一次即可 |
| Mock 与协作 | 需团队工作区与 Mock Server | 内置 Mock、可分享只读文档链接 |
| 离线使用 | 桌面版可离线运行 | 桌面版可离线；在线版依赖网络 |

## 8 测试结论

本轮共执行 48 条接口用例，覆盖任务书要求的 6 个模块，最终 48 条通过。登录鉴权、用户增删改查与口令重置、角色授权与整体替换、部门树的增删改与成环校验、配置读取、日志分页与条件查询、三个统计接口及看板概览均按统一返回格式工作，权限点拦截在 6 个模块上均生效（无令牌 401、越权 403）。

测试同时发现两处"非法输入落到数据库层"的缺陷（DI-01 授权非法权限点返回 500、DI-02 软删除导致同编码新增返回 500），均已在业务层补校验并复测通过，说明"参数校验前置 + 事务保证一致性"这条设计约束在实际代码中仍需逐接口落实。

结论：后端接口能够支持前端页面运行和答辩演示，可作为任务书"核心功能经测试"一项的证明材料。遗留的单元测试、并发测试与数据权限验证列入后续改进，与第 5 节的覆盖说明一并提交。
